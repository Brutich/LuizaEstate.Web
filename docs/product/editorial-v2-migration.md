# Editorial v2 — план миграции главной страницы

> **Статус:** планирование, реализация не начата.  
> **Редакция:** 1 ноября 2026 года.  
> **Epic:** [#55 — Editorial v2 Website Migration](https://github.com/Brutich/LuizaEstate.Web/issues/55).  
> **Дизайн-референс:** [PR #54](https://github.com/Brutich/LuizaEstate.Web/pull/54), `docs/design/concepts/editorial-v2/index.html`.  
> **Репозиторий / целевая ветка:** `Brutich/LuizaEstate.Web`, `develop`.  
> **Источник требований:** этот документ; Issues определяют исполнение, но не заменяют продуктовые договорённости.

## 1. Цель и продуктовые критерии

Заменить текущую одностраничную визитку на согласованный Editorial v2 как полноценную главную страницу **личной практики Луизы**, не меняя платформу и инфраструктуру публикации.

Посетитель должен быстро понять:
1. кто такая Луиза, какие услуги оказывает и где работает;
2. как выбрать подходящий тип обращения;
3. где проверить профессиональные профили и отзывы;
4. как проходит работа и как с ней связаться.

Миграция должна сохранить базовую доступность, поисковую индексацию и конверсионные контактные действия.

**Приёмка по продукту:** визуальное и функциональное соответствие последней утверждённой редакции Editorial v2; никаких новых неподтверждённых кейсов, цен, отзывов, рейтингов или обещаний. Контент, требующий ответа Луизы, не является блокером для переноса **уже проверенных сведений**, но не должен быть придуман для заполнения дизайна.

## 2. Выбранный подход

- **Оставляем:** Astro 6, Node 22, статическую генерацию, GitHub Pages, GitHub Actions, `luiza.estate`, существующие SEO-настройки и Google Analytics.
- **Меняем:** композицию главной, дизайн-токены, разметку секций, карточки услуг, мобильную навигацию и контактные действия.
- **Не копируем** прототип одним HTML-файлом в `src/pages/index.astro`: в Astro должны быть семантические компоненты с обычным CSS и минимальным клиентским TypeScript.
- **Контент сначала в HTML:** сайт должен показывать основные разделы и контакты без JavaScript. Скрипты добавляют интерактивность, но не определяют видимость страницы. Декоративные анимации не могут делать секции невидимыми при ошибке JS.
- **Ассеты:** используем утверждённый портрет `/img/luiza-02.jpg` и локальные оптимизированные изображения; не копируем base64-изображения и внешние ссылки на логотипы Циан/Домклик из экспериментов макета.
- **Репутация:** ссылки на подтверждённые профили [Циан](https://www.cian.ru/agents/164114/) и [Домклик](https://agencies.domclick.ru/agent/866780), без несанкционированных фирменных логотипов и неподтверждённых количественных показателей.

Прототип — визуальный референс, **не production-источник архитектуры и правовых формулировок**. Подробные технические решения допускаются в PR, но существенное новое архитектурное решение требует ADR.

## 3. Состав страницы и поведение

| Раздел | Назначение | Технический принцип |
| --- | --- | --- |
| Header и Hero | Личность, специализация, география, CTA | Семантический статический HTML, локальное фото |
| Услуги (4 карточки) | Продажа, покупка, сложные сделки, юридическая проверка | Одна панель подробностей на выбранный ряд, не растягивать другие карточки |
| Обо мне | Личное ведение сделки и экспертиза | Короткий проверенный текст |
| Отзывы клиентов | Независимое подтверждение репутации | Прямые ссылки на профили, без копирования чужих рейтингов/отзывов |
| Как проходит сделка | Понятная последовательность | Статические четыре шага |
| FAQ | Стоимость, юридическая проверка, география | Доступные `details/summary` |
| Контакты и Footer | Позвонить / написать / email, социальные ссылки | Прямые ссылки, мобильный CTA |

Не добавляем в первом релизе каталог недвижимости, CRM, формы заявки, отдельные SEO-страницы и гипотетические клиентские кейсы.

## 4. Порядок реализации и ответственные задачи

Каждая строка — **одна Issue, одна ветка, один PR в `develop`**. Работы начнутся только после отдельного решения о старте реализации.

| Порядок | Issue | Содержание | Условие завершения |
| --- | --- | --- | --- |
| 1 | [#56 — Design Foundation](https://github.com/Brutich/LuizaEstate.Web/issues/56) | Изолированные стили Editorial v2, типографика Prata/Manrope, базовые элементы, токены | Текущая главная не изменилась, CI зелёный |
| 2 | [#57 — Static Homepage Sections](https://github.com/Brutich/LuizaEstate.Web/issues/57) | Подготовка Astro-компонентов Hero, About, Reviews, Process, Contact | Содержимое доступно без JS, скриншоты соответствуют макету |
| 3 | [#58 — Services & FAQ Interactions](https://github.com/Brutich/LuizaEstate.Web/issues/58) | Карточки услуг, общая панель подробностей, FAQ, мобильные сценарии | Одна панель, ровные карточки, keyboard/no-JS fallback |
| 4 | [#59 — SEO, Quality & Release Readiness](https://github.com/Brutich/LuizaEstate.Web/issues/59) | Подключение новой страницы к `index.astro`, проверка метаданных, аналитики, build-guards и релизной готовности | Все проверки пройдены, production ещё не изменён |

**Точка переключения главной:** в **этапе 4**, когда все секции и интерактивность подготовлены и проверены. Это исключает промежуточный выпуск недособранной страницы. При необходимости локальная/PR-демонстрация компонентов создаётся без индексируемого production-маршрута.

**Зависимости:** сначала завершить дизайн-ревью и согласовать [PR #54](https://github.com/Brutich/LuizaEstate.Web/pull/54). Для аналитики контактных событий переиспользовать существующую [#15](https://github.com/Brutich/LuizaEstate.Web/issues/15), не открывать дублирующую задачу. Если #15 ещё не реализована, согласовать объём её интеграции на этапе 4.

**Выпуск — отдельно после реализации:** проверенный `develop → main` release PR. Само слияние PR этапов в `develop` не публикует изменения: GitHub Pages публикуется только при push в `main`.

## 5. Область затрагиваемого кода (ориентир)

```text
src/
  components/
    layout/                 # Header / Footer при необходимости
    home/                   # Hero, Services, About, Reviews, Process, FAQ, Contact
  layouts/BaseLayout.astro  # сохранить SEO, аналитику, общую структуру
  pages/index.astro         # подключить новую главную только на этапе 4
  styles/
    global.css              # существующие глобальные правила
    editorial.css           # изолированные токены и стили нового дизайна
  scripts/                  # минимальное поведение, если нужно
scripts/verify-build.mjs    # актуализировать проверяемые признаки страницы
public/img/                 # фотографии и оптимизированные ассеты
```

Структура является предложением по организации, а не требованием создать все перечисленные файлы. Не проводить попутный рефакторинг остальных страниц или инфраструктуры.

## 6. Неприкосновенные элементы текущего production

При замене страницы сохранить или осознанно обновить с проверкой:

- `BaseLayout.astro`: `<html lang="ru">`, `title`, meta description, canonical, Open Graph, Twitter Card, `hreflang`;
- связанный JSON-LD граф `WebSite`, `Person`, `RealEstateAgent` с прежними `@id` и только подтверждёнными данными;
- Google Analytics `G-9C9EZBF53F` и корректные контактные события;
- телефон `+7 495 771-55-14`, email `atlas-com@yandex.ru`, основной Telegram `https://t.me/Luiza_real_estate`, существующие подтверждённые социальные ссылки;
- `robots.txt`, `sitemap.xml`, `CNAME`, 404, старые редирект-маршруты `/service-page/`;
- защитные проверки `scripts/verify-build.mjs` и обязательные build-артефакты.

**Особый риск:** `verify-build.mjs` сейчас проверяет буквальные фразы старой главной. На этапе 4 их нужно заменить проверками инвариантов новой версии **без ослабления проверок SEO, контактов и JSON-LD**.

## 7. Критерии готовности и способ проверки

**Автоматически (на каждом PR):** `npm ci`, `npm run check`, `npm run build`; существующий скрипт `verify-build.mjs` должен проходить.

**Браузерно (к интеграции и выпуску):**
- сравнение скриншотов с согласованным макетом на 390, 768, 960, 1440 px;
- отсутствие горизонтального переполнения и неожиданных скачков разметки;
- мобильное меню, FAQ, телефон, Telegram, email и внешние профили;
- выбор/закрытие услуг, корректный выбранный элемент и положение панели при 1/2/4 колонках;
- клавиатура, focus/ARIA, reduced motion; отсутствие ошибок в консоли;
- контент читаем при отключённом JavaScript или ошибке скрипта;
- SEO-метаданные и JSON-LD доступны в сгенерированном HTML, нет непроверенных рейтингов/кейсов;
- контактные действия можно измерить, аналитика не препятствует переходу.

**В релизном PR:** чек-лист smoke-check после публикации, сравнение production-страницы, проверка ссылок и аналитики, план отката.

## 8. Риски и условия остановки

| Риск | Мера |
| --- | --- |
| Переносить дословно баги монолитного HTML-макета | Переиспользовать визуальное решение, переписать поведение как небольшие независимые компоненты |
| Скрипт ломает видимость страницы | Статический HTML по умолчанию видимый, JS — необязательное улучшение |
| Потеря SEO и событий | Не заменять `BaseLayout` без проверки; обновить `verify-build.mjs`, связать с #15 |
| Несогласованные обещания/отзывы/логотипы | Оперировать только подтверждёнными источниками; ограничиться текстовыми ссылками |
| Ветка `develop` содержит другие неготовые изменения | До релиза проверить полный diff `develop → main`, не выпускать посторонние изменения случайно |
| Внешние изображения или тяжёлые base64 | Локальные оптимизированные ассеты, адаптивные размеры |

При выявлении критических регрессий **не выпускать** новую главную до исправления. После публикации возможен откат релизного коммита и повторная публикация предыдущей рабочей версии.

## 9. Не входит в миграцию

- бизнес-интервью и изменение позиционирования без подтверждённых данных;
- реальные кейсы, рейтинг, цены, отзывы без проверенных источников и разрешений;
- новые страницы `/sell-apartment`, `/buy-apartment` и другие SEO landing pages;
- формы сбора персональных данных, CRM, backend, виджеты онлайн-бронирования;
- изменение домена, хостинга, маршрутизации GitHub Pages, внедрение React/Blazor;
- использование фирменных логотипов Циан/Домклик без отдельного правового согласования.

Эти темы ведутся по дорожной карте и отдельным решениям, не расширяют автоматически объем Epic.

## 10. Управление изменениями

- Любое существенное отступление от этого плана сначала обсуждать и фиксировать в `docs/product`, затем синхронизировать соответствующую Issue.
- Если изменяется позиционирование или другое **продуктовое решение**, обновить `docs/product/decisions.md`.
- Для нетривиальных архитектурных решений использовать отдельный ADR.
- После завершения релиза обновить этот документ: фактическое состояние, ссылки на PR и известные ограничения.
